# homecloud — интерфейс фототеки

Две части в одном репозитории:

- **`server.js`** — Node без зависимостей, работает в контейнере на VM
  `family-apps` (192.168.99.20, порт **4180**): раздаёт собранную статику,
  проксирует `/api` и `/media` на бэкенд и решает, кто вошёл.
- **`src/`** — одностраничное приложение на React 19 + TypeScript, собирается
  rsbuild.

Распознавание, модели и каталог — **в другом репозитории**,
`F:\services\homecloud-core`, на машине с видеокартой (порт 18311). Там же
описание моделей и схемы каталога.

Если эта машина выключена, карточка устройства на «Сканировании» может
показать кнопку «Запустить»: `server.js` ходит по SSH (ключ на VM,
`HOMECLOUD_SSH_KEY`) и поднимает `backend.ps1` через `start-remote.ps1`
(лежит рядом с ним в homecloud-core). Настройка и формат команды — README,
«Запуск бэкенда по SSH с фронта»; пользователь/хост/команда SSH хранятся
в `backends.json` рядом с токеном и наружу не отдаются.

## Вход

**Своего окна входа нет.** Учётные записи живут в LLDAP, а вход, имена и роли
выдаёт соседний сервис **`account`** — не картотека. Без сессии интерфейс
уходит на `/auth/start`, сервер отправляет браузер на `/authorize` у account,
тот возвращает его на `/auth/callback` с одноразовым кодом; код меняется на
сессию по внутреннему `ACCOUNT_URL` со служебным `ACCOUNT_SERVICE_TOKEN`, и
фототека ставит cookie `kartoteka_session` на свой хост. Компонент
`components/auth/LoginDialog.tsx` вопреки имени никакой формы не рисует — он
просто перенаправляет на `/auth/start`.

Сессия проверяется у account (`GET /api/auth/me`, кэш 15 секунд). Роль —
`access.homecloud.role`, то есть группа LLDAP `homecloud_admin` /
`homecloud_editor` / `homecloud_viewer`; **от роли в bigfam она не зависит**.
Без группы `/api/session` отвечает 403 `{auth: "forbidden"}`.

Картотека **bigfam** нужна не для входа, а для данных о людях: список для
выбора имени и портреты (`/api/people/<id>/photo`).

Дальше `server.js` ставит бэкенду заголовки `X-HomeCloud-User` и
`X-HomeCloud-Role` (браузерные значения затираются), а на изменяющие запросы
добавляет `X-Local-Token` из `PHOTO_TOKEN`. Роль `viewer` — только чтение: в
интерфейсе это `session.canEdit`.

## Структура

```
src/
  app/          Providers, AppShell, ViewOutlet, маршрут в адресе, опрос
  ui/           ui-kit: 20+ примитивов, у каждого свой .scss рядом
  components/   переиспользуемое, но знающее предметную область
                (nav, notifications, auth, people, albums, features)
  views/        экраны: photos (+viewer, +panel), highlights, people, review,
                training, scan, duplicates, settings, analysis
  store/        zustand, слои в store/slices
  services/     api.ts, queryClient, queryKeys, endpoints/* по темам
  hooks/        useLongPress, useDragScroll, useNativeDialog, useIntersection…
  lib/          чистые функции: format, jobs, adult, storage
  styles/       токены, темы, примеси, анимации, база + index.scss
  types/        domain.ts и api.ts
```

Экранов восемь, а пунктов навигации пять: «Фотографии», «Подборки», «Люди»,
«Настройки» и «Анализ», внутри которого вкладками лежат проверка, обучение,
сканирование и дубликаты (`app/navItems.ts`, `ANALYSIS_VIEWS` в `app/routes.ts`).

«Подборки» (`views/highlights`) — автоматические подборки из
`homecloud-core` (`/api/highlights`): «в этот день», события, месяцы, годы.
Открытая подборка лежит в ссылке (`#/highlights?h=month:2019-12`), а
просмотрщик листает её снимки через `viewer.sequence`, а не галерею. Переключатель
«Почему эти снимки» показывает оценку и причины выбора каждого кадра.

«Люди» (`views/people`): сверху лента «Узнали знакомых» (группы, похожие на
названных), дальше разделы «С именами» и «Без имени». В карточке группы лица
сложены **стопками** (`stacks.ts`; кто с кем — решает бэкенд полем `stack`),
раскрытая стопка встаёт под конец своего ряда, а просмотрщик листает кадры в
экранном порядке. Лицо из ролика открывает видео с начала трека
(`videoStart`, проп `startAt` у просмотрщика). У названного человека — блок
«Возможно, это тоже …» (`/api/person-candidates`). Мыльные лица — группа
`blurry` на «Проверке» (`REVIEW_KINDS` в `PersonCard.tsx`).

## Как принято делить состояние

**Пришло с сервера и перезапрашивается — в TanStack Query. Сделал
пользователь — в zustand.** Опрос раз в полторы секунды (`usePollingStatus`)
иначе перетирал бы то, что человек делает прямо сейчас.

- Ключи кэша — только через `services/queryKeys.ts`. **Режим «скрывать 18+»
  обязан входить в ключ**: иначе после переключения отдаётся старый ответ, в
  котором такие кадры ещё есть.
- Адрес страницы — чистые функции `parseHash`/`buildHash` плюс `hashSync`,
  работающий вне React. Смена экрана кладёт шаг в историю, правка фильтров —
  нет, иначе «назад» превращается в отмену каждого щелчка.
- Сетка снимков: `PhotoTile` подписан на **свой** бит выделения, а не получает
  его пропом — иначе щелчок по одной плитке перерисует все двести.

## Стили

SCSS, обычные имена классов, файл рядом с компонентом. `styles/index.scss`
подключает основание и примитивы ui-kit и **импортируется в `main.tsx` раньше
`App`**: классы примитивов используются и обычной разметкой (`a.button`,
`span.chip`), и в каскаде обязаны идти раньше стилей экранов.

## Чего нельзя делать

- **Никакого CSS-in-JS.** `server.js` отдаёт
  `style-src 'self'` без `unsafe-inline`: инъекция `<style>` и атрибут
  `style="..."` внутри строки разметки на проде молча не работают. `style={{}}`
  в React безопасен — он пишет через CSSOM.
- **Атрибут `hidden` и класс `.hidden` — разные вещи.** Условный рендер по
  умолчанию; класс `.hidden` — только там, где узел обязан остаться в DOM ради
  перехода; атрибут `hidden` — никогда.
- **`photoMediaUrl` (`services/media.ts`) закреплён таблицей-тестом.** Он
  решает, замылен ли кадр, и зашивает решение в адрес, а значит и в кэш
  браузера. Любая правка правил — сначала строка в таблице, потом код: ошибка
  здесь означает откровенный кадр, показанный без замыливания. `adultMode` и
  `zoom` обязаны быть входами отрисовки плитки.
- **`<dialog>` открывается через `showModal()`, а не атрибутом `open`** —
  иначе окно немодальное, без подложки и ловушки фокуса. См.
  `hooks/useNativeDialog.ts`.
- **У каждого эффекта — настоящая уборка.** StrictMode выполняет их дважды:
  повторный `showModal()` бросает, повторные `observe` и `subscribe`
  удваиваются.
- **Новая зависимость должна попадать в `package-lock.json` тем же коммитом** —
  `deploy.ps1` делает `npm ci`.

## Поведение, которое выглядит как недосмотр, но им не является

- Карточки активных задач висят, пока их не закроют руками, а обычные тосты
  гаснут за пять секунд. Это прямая просьба пользователя.
- Сбор описи заканчивается одним из четырёх сообщений (ошибка / всё ещё идёт /
  остановлено / готово) — это единственный сигнал о молча упавшем задании.
- Просмотр лиц из карточки группы не закрывается шагом назад по истории: под
  ним открыта сама карточка, и шаг назад закрыл бы её.

## Команды

```bash
npm run typecheck && npm test && npm run build
npm run dev          # проксирует /api и /media на 127.0.0.1:4180
```

Прод-сборку смотреть **через `node server.js`**, а не через dev-сервер: только
так всплывают нарушения политики безопасности (`Refused to apply inline style`
в консоли) и проверяется, что CSS вынесен в файл.

## Публикация

`deploy.ps1` кладёт **исходники** (не собранный `dist/`) в
`amagomedsharipov@192.168.99.20:/opt/homeapps/homecloud` и запускает
`sudo docker compose up -d --build homecloud` в `/opt/homeapps`. Сборка идёт
внутри контейнера по многоступенчатому `Dockerfile`; локальные `npm ci` и
`npm run build` в скрипте — предполётная проверка, что оно вообще собирается.

Compose общий на четыре сервиса: `homecloud`, `bigfam`, `account`, `lldap`.
Переменные — из `/opt/homeapps/.env` (`PHOTO_BACKEND`, `PHOTO_TOKEN` и
секреты соседей), адреса соседей задаются по именам контейнеров. Реестр
устройств: `/srv/homeapps/homecloud` на хосте смонтирован в
`/var/lib/homecloud` внутри контейнера.

Правки делать здесь и публиковать скриптом, а не на месте. После
пересоздания `backend-token.txt` на Windows надо обновить `PHOTO_TOKEN` в
`/opt/homeapps/.env`, иначе изменяющие запросы получают 403.

В репозитории остались от прежней схемы (служба systemd прямо на хосте pve)
два файла, которые ни во что не собираются: `systemd/homecloud.service` и
корневой `docker-compose.yml` — настоящий compose живёт в `/opt/homeapps`.
